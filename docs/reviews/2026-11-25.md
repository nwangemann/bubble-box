# Review and status, 2026-11-25

A review of the app, the docs and the development process at a pause, after the calm room, Showdown, 8-ball and sound were built. The changes from this pass are listed under each heading and landed together.

## Status

- **Plan:** sections 1 to 4 are built. Open work is showdown trails (5), liquid-filled bubbles (6) and the store listing (7). Section 10, everything that needs a person and a phone, has not started.
- **Build:** `main` was clean and in sync with GitHub before this pass. `npm run check` passes: types, lint, formatting and 234 tests in 22 suites.
- **Size:** about 14,800 lines of app TypeScript (including SkSL in strings) in 118 files under `src`, 3,300 lines of tests, 4 ADRs, 51 commits over two days.
- **Verified vs not:** everything was checked in tests and on the iOS simulator or in the web preview, with frame times recorded in the plan (60 fps throughout on the simulator). Nothing has been judged on a physical phone: feel, haptics, sound, real frame times and VoiceOver.

## The application

Strengths:

- **A clear core.** `src/core` is plain TypeScript worklets with no React, Skia or Expo imports, and every tunable number is in `src/config`. The rule holds everywhere; no exceptions were found.
- **One thread for the loop.** Touch, physics and drawing run on the UI thread; React renders only when an option changes. An empty room draws nothing.
- **Depth without a 3D engine.** Per-bubble shaders with computed normals, a ray-marched merge, shadows and light thrown on the walls. It reads as 3D in every screenshot.
- **Tested rules.** 8-ball contacts, fouls, groups, the called 8 and the opponent are covered by tests; the ruleset and the opponent's strength came from simulated games.
- **Hygiene.** Strict TypeScript, clean lint and format, no TODOs, no `any`, no suppressed lint rules, one intentional `console.warn` for unsaved settings.
- **Honest records.** Every built step in the plan says what was seen, how, and what was not.

Gaps and risks:

- **No phone verification.** This is the largest risk. The plan's own MVP bar ("a stranger understands it without words, and it holds 60 fps with 10 bubbles") cannot be met until section 10 starts.
- **Scope.** Twelve styles, nine boxes, eight meeting and ten pop effects, six arenas of twelve entrants, and an 8-ball mode. The plan already schedules a reduction (7.4); a portfolio reader sees the breadth, but a store user would benefit from fewer, stronger defaults.
- **No live demo.** A reviewer has to clone and build to try it. The web preview already runs the app in a browser; hosting it needs relative asset paths (the page preloads `/canvaskit.wasm` from the site root) and a host that serves the WebAssembly correctly.
- **Web-only polish.** In the browser, the Tap tile shows "New bub…" at phone width: `adjustsFontSizeToFit` shrinks it on iOS but not on the web. Left as is, since the web build is a preview.
- **Unused exports.** About 40 types and helpers are exported but used only in their own module. Harmless, left alone.

## Process

The work followed one loop: a plan of session-sized steps, one step per session, built and checked by the agent, recorded in the plan with what was and was not verified ([ai-workflow.md](../ai-workflow.md)).

What worked:

- **Written state over chat history.** `AGENTS.md`'s file map and the plan's **Built** notes let each session start cold.
- **Explore, then reduce.** Ideas were tried cheaply and dropped with a recorded reason, so none came back.
- **Measured drawing.** Every step that draws recorded its frame time on the simulator.
- **Manual checks last.** Everything only a person can judge collects in one section and never blocked work.
- **Rules learned once.** A worklet failure that only the UI thread showed (a default parameter that was not captured) became a rule in `AGENTS.md`.

What cost time or needs attention:

- **Personal details in history.** The first commit's author email is a machine hostname. The repository is public and this commit is pushed; removing it needs a history rewrite and a force push.
- **Long Built notes.** The plan's **Built** section is the verification log, but some entries run to ten lines. Future entries could be shorter, with detail in commit messages.
- **No gate before this pass.** There was no CI or pre-commit hook; `npm run check` relied on the session routine.
- **Large first commit.** The first feature commit holds the whole first version, so history starts coarse.

## Recommendations

In order of value for a portfolio reader:

1. **Rewrite the first commit's author** to the GitHub no-reply address and force-push, before the repository gets more attention.
2. **Set the GitHub description and topics** (for example `expo`, `react-native`, `skia`, `reanimated`, `shaders`, `physics`, `typescript`), and push so CI runs and a badge can be added.
3. **Host the web preview** as a live demo, after making its asset paths relative. This needs a decision on hosting.
4. **Start section 10 on a phone**: feel, frame time and haptics first (2.1, 2.2), then the reduction in 7.4.
5. **Compress the large PNGs** and, once phone checks pass, tag `v1.0.0`.
